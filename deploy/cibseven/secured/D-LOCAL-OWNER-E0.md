# E0: parent-installed ingress and initial source review

Status: additive contract/source proposal for independent review. This slice supplies inert records and comparisons only. It does not install a supervisor, create SQLite state, authenticate AWS/PG, acquire credentials, sign an owner decision, or authorize an effect. Existing L1 v1 policies, ten DynamoDB anchors, state machine and historical D migrations remain unchanged.

## 1. EF-01: real synthetic parent installation is permitted

The user authorized disposable synthetic engineering/provisioning. A newly generated synthetic key, dedicated UID and supervisor may qualify when actually installed under the real external parent authority and independently verified. The forbidden shortcut is requester-generated material merely asserted to be authoritative. No preexisting owner HTTP service or extra user permission is required by this E0 contract; actual external parent identity/resource authority is still necessary for live qualification.

The parent installer is a concrete finite producer still to implement and review. It verifies the actual authorized parent credential/key, creates the dedicated OS/source/store installation and independently measures the resulting identities. It signs the installation record only after those real steps. A parser, local file lock, SQLite pragma, supplied hash or self-signed key cannot stand in for this operation.

### Closed installation record

`maezo.d7-local-owner.ingress-installation.v1` has exactly `protocol authority_id parent_operation_id parent_subject parent_key_id intent_sha256 owner_key_id owner_key_sha256 source_artifact_sha256 not_before_ms expires_at_ms supervisor store uids`.

- IDs are existing D UUID; parent_subject/key IDs existing Id; digests existing Sha256. Lifetime positive and <=900000ms, within the genuinely installed parent grant. Parent authorization binds exactly one OwnerIntent hash, not a caller-chosen family of future requests.
- `supervisor` exactly `instance_id boot_id pid start_ticks uid executable_sha256`. IDs are UUID; pid/start_ticks positive; uid UInt. Values come from the parent-observed actual Linux boot/process identity after creating the child, not the child's self-report. The parent-controlled launcher has no arbitrary executable/UID/env choice. Its exact source and dependency artifact is independently qualified and not writable by requester/worker/readback.
- `store` exactly `store_id absolute_path device inode owner_uid schema_sha256 initial_anchor_sha256`. Store UUID and source-fixed schema hash identify one actual freshly initialized store. Path is absolute canonical POSIX, no empty/dot/dotdot/NUL components, <=4096 bytes. Device UInt, inode positive. Parent-observed actual file identity is pinned. SQLite/sidecars/private directory custody is qualified as a whole; matching inode alone is insufficient.
- `uids` exactly `owner reader requester`, UInt pairwise distinct; owner/reader are nonzero dedicated UIDs. Store owner_uid equals owner UID. Supervisor UID may be the separately authorized privileged launcher; no auto-installation or arbitrary privilege elevation is supplied here.
- Owner key ID/hash must equal the separate OwnerIntent trust. Source artifact hash must equal actual installed source and the intent's artifact binding. The parent signer key is independently installed upstream; it must not be selected from this record's key_id field. The newly generated owner key need not preexist the real parent installation.

### Closed signature domain

All E0 records use existing canonical D JSON/depth32/safe integer rules, max131072 bytes. Signature envelope exactly `protocol kind key_id body signature`, protocol `maezo.d7-local-owner.e0-signed.v1`. Signing input is `b"maezo.d7-local-owner.e0-signature.v1\0" + canonical({protocol,kind,key_id,body})`, Ed25519 canonical unpadded base64url64-byte signature. Kind is `installation`, `ingress`, `candidate` or `review`. Shape/message helpers perform no cryptographic verification or authority admission. Actual parent installation verification and owner review signature verification remain distinct future fixed consumers with independently supplied trust.

## 2. Durable ingress claim and nonreuse

Before the preparatory owner AssumeRole, one atomic SQLite transaction inserts all ten permanent key pairs from L1 `reservation_keys(intent)`, plus `D7INGRESS#AUTHORITY#<authority UUID>/RESERVATION`, `D7INGRESS#STORE#<store UUID>/RESERVATION`, `D7INGRESS#SUPERVISOR#<instance UUID>/RESERVATION`, and the initial ingress EVENT. Full identical canonical binding contains installation record hash, exact intent hash, store/supervisor identities and immutable request/source association. No INSERT OR REPLACE, upsert, update, delete, TTL or partial fallback. The exact schema bytes are frozen as INGRESS_SCHEMA in owner_local_e0_contracts.py; the persistent transaction consumer remains unimplemented. SQLite>=3.37 STRICT tables, no extension loading, trusted_schema=OFF, recursive_triggers=ON, foreign_keys=ON, synchronous=FULL and journal_mode=WAL are required when the actual consumer is reviewed. Busy/lock uncertainty refuses without retry. These settings alone do not prove durability or custody.

The complete original ten-key collision domain is retained: installation, run, complete Scope including database incarnation, control-scope, enrollment, bootstrap operation, acquisition and exact three resource ARNs. Changing operation UUID, enrollment, profile alias, store name or supervisor does not create permission under the same installed authority: the parent installation binds one exact intent/store/process. The original distributed DynamoDB eleven-put claim remains mandatory later, before any role/table creation or bootstrap/readback issuance. A local ingress reservation does not replace it.

Ingress EVENT PK is `D7INGRESS#AUTHORITY#<authority UUID>`, SK `EVENT#<10 decimal revision>`. Exact record fields: `protocol installation_sha256 intent_sha256 store_id supervisor_instance_id revision state previous_sha256 evidence_sha256 recorded_at_ms`; protocol `maezo.d7-local-owner.ingress.v1`. Revision1 CLAIMED has no prior/evidence. Normal states:

`CLAIMED -> ISSUE_STARTED -> ISSUED -> DELIVERY_STARTED -> DELIVERED`.

ISSUE_STARTED is durable before the one real owner AssumeRole; ISSUED requires the actual request/response/identity/expiration receipt, not a requested hash. DELIVERY_STARTED is durable before its one in-memory transfer to the factory portion of the same process; DELIVERED requires the actual retained handle/process acknowledgement. UNKNOWN is reachable from every nonterminal state and terminal; DELIVERED terminal. No transition resets, retries, resumes or reissues. Every append compares exact prior bytes/hash and inserts the next event absent-only in one SQLite transaction. Later outcome readback grants historical evidence only.

### Fixed store and anchor bytes

The schema has exactly two STRICT WITHOUT ROWID tables: `ingress_installation(singleton INTEGER PRIMARY KEY CHECK(singleton=1), record_bytes BLOB, record_sha256 TEXT)` and `ingress_records(PK TEXT, SK TEXT, kind TEXT, record_bytes BLOB, record_sha256 TEXT, PRIMARY KEY(PK,SK))`. All nonkey columns are NOT NULL; record bytes1..131072; hashes exactly64 lowercase hex; kind is reservation/event. Fixed before UPDATE/DELETE abort triggers on both tables forbid mutation; recursive_triggers=ON is mandatory to prevent INSERT OR REPLACE from bypassing deletion triggers. The consumer never emits REPLACE/upsert SQL. There is no mutable metadata/head table. The actual consumer compares full installed sqlite_schema to these source-fixed statements and rejects extra tables/triggers/indexes/views before use; no user-defined functions/extensions are admitted. Parent creation/installation and initial record insertion are not implemented here.

`store.schema_sha256` is exactly SHA256(INGRESS_SCHEMA). Its initial anchor is canonical `{protocol:"maezo.d7-local-owner.ingress-anchor.v1", authority_id,parent_operation_id,intent_sha256,source_artifact_sha256,supervisor,store}`, with the complete store object **excluding initial_anchor_sha256** to avoid a self-hash cycle. The parent-signed installation binds that digest; the stored singleton record is the actual complete canonical signed installation packet. The parser checks the anchor recipe; only the future parent installer/current reader can prove the actual file contains it. File/row/hash reproduction is not re-enrollment authority.

### Continuity and rollback refusal

This first profile authorizes **one live parent-installed supervisor epoch for one intent**. It is not a crash-resumable owner issuer. Before and after each durability/effect boundary, the concrete supervisor must independently inspect actual boot ID/PID/start ticks/UID/executable and store path/device/inode/owner, compare them to the parent-signed installation, and maintain a private in-memory highwater/hash plus an irreversible consumed-before-call flag. That witness is created by the parent-installed process and is not supplied by a requester. It advances only after verified durable append; the flag is set before calling STS, with no code path that clears it. Uncertain state ends that epoch.

Copy/replacement to a new inode/path fails identity. In-place rollback/truncation/reordered history in a still-live epoch fails the retained highwater/hash/full-history readback. A copied full journal remains consumed, not a new claim. After process death or machine reboot, the signed process identity no longer matches: every new process enters **recovery-only**, even if the SQLite rows look empty or correct. A restarted process cannot recreate the live witness or treat later successful readback as the winner. PID reuse is insufficient because boot ID/start ticks differ. No effect resumes after an unexpected disconnect from the parent supervisor.

The concrete installation also needs enforced source/credential/FD custody: no second supervisor may access the ingress credential or change this record/store under the same parent grant. A second process copying the public record fails its actual measured process binding; a second source path with the same broad credentials means the installation was never qualified. The trusted parent administrator can revoke and provision genuinely separate future authority, but cannot describe that as recovery/reissue of this consumed authority. Replacement/re-enrollment must preserve and check prior owner-installation/source/run/scope/resource reservations; it needs a separately reviewed parent operation and is unsupported by this v1 issuer. SQLite/file permissions alone do not prove exclusion against the parent administrator.

`compare_continuity_values` in this inert slice only compares typed record values. It does not inspect a kernel process, read SQLite or create a capability. Effect code must obtain these values itself through the qualified supervisor, not pass a matching caller dictionary. Private readback is independently retained before admitting the next effect.

For initial REVIEWED/UNRECONCILED ROOT only, `candidate_sha256` is SHA256 of the canonical complete **InitialSourceCandidate** bytes, including this domain/purpose. ## 4. EF-03: L1→L2 remains an unallocated capability

Generic `_closed_observations` still rejects every supplied session/prepared transaction/route; no empty-array projection is provided here. L3 deployment/grant/broker/native/Q2 authority is absent.
