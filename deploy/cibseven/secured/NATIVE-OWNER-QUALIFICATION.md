## 2. Scope and durable owner storage

Allocate `maezo_native_owner_v1`, outside both frozen runtime `maezo_native_v2` and D `maezo_d7_control` namespaces. Allocate a new separately versioned owner installer/manifest; never edit existing installed native/D migration bytes, schemas, function ownership or helper ABI. No application startup DDL.

Two owner-only relations:

1. `installation`: one immutable owner-store installation row, UUID, source/manifest/DDL digests, actual DB/schema/role identities, full exact catalogue/ACL manifest and digest. Own schema/table/function inventory is separately pinned; do not pretend it belongs to the frozen six-table runtime allocation.
2. `principal_qualification_receipt`: immutable technical request/result bytes+SHA256, native_owner_operation_id UUID primary key, actual native installation digest, D preparation UUID, scope and generation/principal selectors, owner session/effective identities, recorded-before-commit timestamp. Unique `(native_installation_receipt_sha256,d_preparation_id)` and unique operation identity prohibit replacement initial qualification. Bytes are canonical, closed and <=1MiB; full byte equality accompanies digest equality.

Reuse the existing native schema-owner role for owner-store ownership. Require an already qualified authenticated migration session with existing inherited native-owner and D-owner authority; SESSION_USER equals CURRENT_USER and both names/OIDs match reviewed bindings. No owner role impersonation, new membership or automatic grant escalation. If the existing route lacks the narrowly required owner read/write privilege, refuse and report its exact missing privilege.

Owner schema/tables/functions grant nothing to PUBLIC, runtime login, native function owner, native issuer, D guard-function owner, D issuer login or worker. D verification runs through its separately authenticated migration owner, using that already qualified inherited native-owner route. Install before capturing D baseline when possible; if installed afterward, prove the full D grant/membership catalogue remains byte-identical. New grants to D protected roles are not silently permitted.

Enforce append-only rows with trigger/ACL and exact replay; no UPDATE/DELETE/down migration. The schema owner remains a trusted owner like existing D storage, not a claim of resistance to an omnipotent DB administrator.

## 3. Initial qualification contract and transaction

Operation is `qualify_initial_installation`, limited to the already installed first prepared runtime/candidate principal. No later login, rotation, restore promotion, native ACL amendment, production activation or registration.

Closed input: protocol/version, owner_operation_id, owner-store installation_id, exact D installation_id and preparation_id, expected native installation record digest, scope, generation_id, purpose, login_name/login_oid, generation_core_sha256, decision_sha256, database_binding_sha256 and expected complete before native catalogue digest. Every value is an expectation; actual owner/current DB observations establish facts. No secret values or direct caller privilege grants.

Define `NativeInstalledRecordV1` as the canonical complete projection of the actual original native schema_version row, retaining every original scalar field and complete preparation_binding, with preparation_receipt_bytes encoded as canonical base64url. Its SHA256 is `native_installation_receipt_sha256`. The existing opaque migration_receipt remains an identifier inside this projection and is never used alone as authority. This is a new explicit normalization of the actual installed record, not a fabricated execution receipt or a claim about unobserved prior SQL transactions.

Lock order is D F -> exact G -> D V -> exact immutable D PREPARED receipt -> owner-store installation row -> exact owner-operation identity/receipt. All operations in this proposal, including D consumer verification, use this order; no native-owner lock followed by a D lock. Use bounded READ COMMITTED owner transactions and the original installation/statement budgets. Recheck the exact original prepared state under locks before commit.

Owner qualification independently verifies:

- actual PG16 session/database/ACT namespace and separate owner identities;
- unchanged D source/installation/helper identity and fixed ABI;
- exact original PREPARED bytes/hash/Core/principal and current G decision, NOLOGIN/no CONNECT, no opened/retired timestamps;
- current F CLOSED/no current generation/RECONCILED, current owner run and epoch;
- exact installed native record/source/19-function/six-relation catalogue, ownership/default ACLs and native runtime/issuer privilege allocation;
- own owner-store source/catalogue/ACL custody;
- unchanged native catalogue at the end of the operation.

Because initial qualification makes no native ACL change, the outer before_catalog_sha256 and after_catalog_sha256 are equal actual native runtime catalogue hashes. They describe this qualification operation, not an invented pre-installation snapshot. D catalogue adoption below separately compares its actual prior PREPARED catalogue against the actual newly installed native catalogue delta.

Inner native receipt is a closed `maezo.native-owner-initial-qualification-receipt.v1` document: operation identity+request digest, owner-store installation identity, complete NativeInstalledRecordV1+digest, exact D preparation/Core/decision/scope/principal bindings, before/after catalogue manifests+hashes, actual owner session/effective name/OID, and database timestamp. Persist these bytes and the outer 17-field binding projections in the same owner transaction. Return COMMITTED only after actual commit. Commit ambiguity is UNKNOWN with no successful receipt claim; authenticated exact-operation readback resolves it. Exact replay returns retained bytes after current owner/catalogue/precondition checks, without a second INSERT. Reused ID with changed bytes or second initial operation for the same preparation conflicts.

The producer emits the existing outer `maezo.d7-native-principal-qualification-binding.v1` from the committed row. `native_receipt_bytes` holds the inner persisted bytes; its SHA matches the outer field. All scope/generation/purpose/login/Core/decision/database/helper/install/cat fields must agree with the inner row. The frozen diagnostic `native_installation_readback` evidence cannot be substituted.

## 4. D consumer and the source-level catalogue transition

Current source has a real composition cycle: `_owner_context` unconditionally calls `_assert_catalog(target_oid)` before `NativeOwnerAuthority.verify`. `_grant_catalog` includes every maezo_native_v2 grant; the original PREPARED catalogue predates native installation. Excluding only the prepared runtime OID still leaves new native function-owner/issuer/schema-owner grants, so the current guard rejects before a NATIVE_QUALIFIED event can retain the new actual catalogue.

Implement an exact native-owner transition branch only for NATIVE_QUALIFIED in the explicit D owner installer. Ordinary issuer/runtime SQL guards, other owner operations and frozen SQL stay unchanged. This is the existing manifest's NATIVE_ACL capability made concrete, not a permissive catalogue exception.

- Acquire the original D owner locks and validate D installation/object definitions/owners, current role attributes, scope/database and complete recursive membership closure before considering a transition.
- Give the concrete native verifier the SAME enlisted owner cursor (explicit Python owner-port signature extension; no hidden second connection), exact event/birth/G bytes and previous complete owner catalogue.
- Read the immutable native owner-store row by operation ID, validate current owner-store source/ACL custody and byte/hash equality, and independently recheck current native record/catalogue/source against the retained receipt. Possession of a supplied receipt is insufficient.
- Compare the complete actual D/native grant catalogue against the prior PREPARED manifest. Allow only the exact initial native allocation reconstructed from the reviewed native installer manifest, actual object OIDs/owners and receipt. The only non-native additions are the frozen ACT schema USAGE and eleven ACT_RU_EXT_TASK column SELECT grants described in §4.1. Preserve every existing object definition, owner and grant tuple. No other D/non-native delta, role/membership change, PUBLIC grant, altered grantability or extra native object is permitted. No arbitrary caller-provided allowlist or ignored fields.
- The verifier returns exact verified current catalogue bytes, not a Boolean bypass. Persist the NATIVE_QUALIFIED D event and that actual catalogue through the existing owner receipt path in the same D transaction, then execute the original `_assert_catalog()` against the newly retained snapshot before commit.
- Replays also revalidate current native receipt/catalogue authority before returning historical D result. Ordinary `_replay` currently bypasses the NativeOwnerAuthority call; route this event's replay through the concrete verification first.
- No source path opens LOGIN, grants CONNECT, calls native registration or advertises readiness. Later existing D issuer operations still require their own actual controller observations, proofs and native-qualified event.

If the exact transition cannot satisfy frozen D installation object digests without changing SQL, stop and allocate a separately versioned D migration. Never replace a historical SQL function or mask drift. The intended Python-only owner transition must prove all ordinary immutable invariants independently before admitting the exact native delta.

## 4.1. NOQ-01: exact initial native and ACT allocation

The expected addition set is reconstructed from the frozen native SQL package and qualified installer identities, never from a caller-supplied allowlist or simply accepted from observed ACLs. Native namespace grants must match the pinned schema/table/column/function definitions, exact six relations and nineteen functions, native schema/function-owner and issuer/runtime identities, actual OIDs, signatures, grantor, privilege and grantability. Include the implicit owner ACL entries exposed by the frozen D `_grant_catalog`; owner privileges are not arbitrary exceptions. Validate actual ownership against the recorded installation and package independently before deriving those entries.

Outside the native namespace, permit precisely these source-pinned additions (`native-acquisition-v2-postgres.sql:67-68`):

- ACT schema USAGE: actual `act_schema` name and namespace OID from NativeInstalledRecordV1, grantee equal to the qualified native function-owner OID, exact authenticated grantor proven by the reviewed native installation execution identity and effective grant authority, `grantable=false`.
- Eleven separate column SELECT entries on that ACT schema's actual `act_ru_ext_task` relation OID: `id_`, `tenant_id_`, `proc_def_id_`, `proc_inst_id_`, `execution_id_`, `topic_name_`, `worker_id_`, `lock_exp_time_`, `suspension_state_`, `retries_`, `rev_`. Each has exactly one named column, no function arguments, the same qualified native function-owner grantee, independently bound grantor, SELECT privilege and `grantable=false`. Pin relation/column identities and unchanged object owner; reject dropped/replaced columns and replacement relation OIDs. Do not infer the grantor from whichever current ACL happens to exist.

Set comparison is `actual_complete_grants == expected_previous_with_authenticated_dynamic_overlays UNION exact_source_allocation`, with canonical full tuple equality. Existing entries must survive byte-for-byte; if a source allocation entry already existed identically it is retained, never duplicated. No removal or mutation is permitted. Compare `object_class`, schema/name/OID, function argument types, exact column list, grantee/grantor OIDs, privilege and grantable flag. Source allocation cannot authorize broader ACT table SELECT, CREATE, extra columns, inherited privilege, PUBLIC, another schema or another role.

Native catalogue_v2 omits ACT ACLs. Therefore independent complete D catalogue comparison is mandatory even when native before/after digest remains unchanged. A native digest match alone never qualifies the ACT boundary. Missing independent installer/grantor authority causes refusal; observed ACLs do not manufacture that authority.

## 4.3. Current qualification versus historical reconciliation

`qualify_initial_installation` exact replay and D consumer replay require current owner/source/catalogue and initial prepared-state checks. A separately authenticated `read_committed_operation` may return the exact durable historical row to resolve UNKNOWN after commit ambiguity; its response explicitly says HISTORICAL_COMMITTED and does not assert present admission, lease validity or unchanged runtime state. Neither API creates leases, revokes principals, renews LOGIN/CONNECT, restores generations or supplies Q2 authority. D/NATIVE_QUALIFIED and later issuer paths retain their own current admission prerequisites.

## 7. Implemented source composition and upstream prerequisites

The implementation is an explicit migration-owner API. It does not discover credentials, compose a controller, start services, or seed protected D rows.

1. Obtain genuine upstream D control and database installation/owner-resource evidence. Initial reconciliation requires the actual `close_runtime_fence` receipt before the qualified `INITIAL_RECONCILIATION` root transition and generation reservation. An owner `PREPARED` principal birth alone is insufficient: the real D SQL `prepare_generation` operation must also create the exact `MZO_RUNTIME_ADMISSION` generation, still PREPARED/UNADMITTED and NOLOGIN/no CONNECT. Missing F/G/birth/state produces refusal.
2. Install the separate owner store with `migrations/native_owner_qualification_install.py::install` in an explicitly owned READ COMMITTED transaction. Supply its protected, independently pinned manifest and SQL bytes plus `StorePins`; installer returns observed custody bytes, and the caller owns commit/rollback/UNKNOWN handling. Prefer before D installation. A late install executes the original D catalogue assertion and proves no complete D grant delta, including current event-manifest role inventory.
3. Use the actual original native installer binding with `migrations/native_owner_readback.py::FrozenNativeReadback`. Supply independent SHA256 pins for `install_v2.py`, the frozen native manifest and frozen SQL template. Source verification uses the exact hashed byte bundle, without rereading assets during rendering. Additionally pin actual ACT schema and external-task relation owner OIDs. This initial profile requires the authenticated migration principal to inherit those owner routes; its ACT grantors must equal the corresponding object owners. Another GRANT OPTION route is refused, not inferred from current ACLs. Unsafe default-ACL future grants are refused.
4. Compose the existing D `OwnerInstaller` with its actual `OwnerAuthority`, the same already qualified connection, and `NativeQualificationOwner(connection, store_pins, frozen_native_readback, d_owner)`. Explicitly assign this concrete object as `d_owner.native_authority`; there is no accepting default or application/controller startup wiring. The source author supplies no AWS OwnerAuthority implementation or invented resource manifest.
5. Submit the closed `maezo.native-owner-initial-qualification-request.v1` canonical bytes to `qualify`. Full original `schema_version` bytes and authentic D birth/G/F readback must match. The producer calls the existing external OwnerAuthority replay/readback port using the original authentic PREPARED request/result before retaining the new operation. It holds D locks before the owner-store installation lock, persists one immutable receipt, rechecks current source/catalogues, and reports COMMITTED only after connection commit. Commit ambiguity or failed rollback returns UNKNOWN without successful binding bytes.
6. D event ingestion receives the committed outer binding from that operation. Its concrete verifier uses the exact enlisted D cursor, authenticates protected owner-store/source/ACL custody, verifies inner/outer byte equality and current native/D evidence, and applies the complete invariant matrix plus exact allocation. PostgreSQL MVCC hides other transactions' uncommitted rows; readback also rejects the current full top-level transaction through `creator_top_xid`, which an immutable, database-controlled BEFORE INSERT trigger stamps even beneath savepoints or PL/pgSQL subtransactions. The trigger overwrites caller-supplied values; a just-inserted uncommitted row cannot establish the prior committed operation. The supplied D cursor must belong to the configured connection before any observation. NATIVE_QUALIFIED replay performs current native verification before returning history. The original D SQL assertion remains mandatory after event append before commit.
7. `read_committed_operation` returns only HISTORICAL_COMMITTED evidence to resolve an UNKNOWN outcome. It never promises current admission or lease validity. No API here issues LOGIN/CONNECT, native registration, readiness, Q2 purpose authority, restore or rotation.

Finite tests cover closed bytes, storage custody, source extraction, exact ACT grants, full guard families and transaction/port order. Their synthetic records are test vectors only. PostgreSQL owner-store mechanics, live upstream controller/AWS qualification, positive native/D admission, Native30/D53 and engine acceptance remain separate **NOT_RUN** gates until their real inputs and execution window are available. Final composed source requires independent source review and a provenance-pinned artifact rebuild.
