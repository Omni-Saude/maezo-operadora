## 1. The defect, exactly (B1 — verified at HEAD `a0427d2`)

There is **no way to run this system**. Three independent facts:

1. **No entrypoint anywhere.** `grep -rn "__main__" src/` → nothing; `pyproject.toml` has **no**
   `[project.scripts]` (`pyproject.toml:1-95`, only `[project]`/deps/tool config). Every Helm Deployment
   invokes a `python -m …` module that does not exist:
   - `deploy/helm/maezo-tenant/templates/deployment-worker-daemon.yaml:50` →
     `command: ["python","-m","maezo.runtime.worker_runtime"]` — module absent.
   - `deploy/helm/maezo-tenant/templates/deployment-agent-runtime.yaml:71` →
     `command: ["python","-m","maezo.runtime.agent_runtime"]` — module absent.
   - The gateway pod is already **disabled** for exactly this reason:
     `deploy/helm/maezo-tenant/values.yaml:113-127` ("orphaned Deployment with no runnable module …
     `python -m maezo.gateway` … cannot be directly executed → the pod CrashLoopBackOffs").
2. **No external-task dispatch loop.** `src/maezo/runtime/` contains `harness.py` (a LangGraph
   `StateGraph`, `harness.py:28-113`), `checkpoint.py`, `inference.py`, `metrics.py` — none of which
   fetches or completes a BPMN external task. There is no `fetchAndLock` caller in `src/` at all.
3. **The worker registry is dead.** `WorkerRegistry` + `WorkerBase.run()` (retry + metrics) exist and are
   correct (`src/maezo/tools/workers/base.py:40,107-185,214-281`) but **only tests construct them**; no
   production code ever calls `worker_registry.register(...)` or dispatches by topic.

Consequence: the 16 worker modules, 18 BPMN processes (`spec/processes/bpmn/*.bpmn`) and 54 DMN tables are
inert. T1.1 builds the spine that makes them run; T1.2 (ADR-0026) makes all 16 modules registrable.

## 2. Engine facts (CIB Seven `2.1.0` — the version in `docker-compose.yml`)

`docker-compose.yml:45-64`: service `cibseven`, image **`cibseven/cibseven:2.1.0`**, port `8080`,
healthcheck `curl -sf http://localhost:8080/engine-rest/version`. CIB Seven 2.x is the community fork of
**Camunda Platform 7**; it preserves the Camunda 7 REST contract under the base path **`/engine-rest`**
(the healthcheck at `docker-compose.yml:60` confirms `/engine-rest/version` on this exact image).

**External-task REST endpoints the spine uses** (all under `/engine-rest`, verified against the CIB Seven
2.0 manual, *External Tasks*, and the Camunda 7 REST reference the fork mirrors):

| Op | Method + path | Request body (key fields) |
|---|---|---|
| Fetch & lock | `POST /external-task/fetchAndLock` | `workerId`, `maxTasks`, `usePriority`, `asyncResponseTimeout` (long-poll ms), `topics:[{topicName, lockDuration, variables[]}]` |
| Complete | `POST /external-task/{id}/complete` | `workerId`, `variables` (Camunda-typed), `localVariables?` |
| Report failure | `POST /external-task/{id}/failure` | `workerId`, `errorMessage`, `errorDetails?`, **`retries`**, **`retryTimeout`** (ms) |
| Report BPMN error | `POST /external-task/{id}/bpmnError` | `workerId`, `errorCode`, `errorMessage?`, `variables?` |
| Extend lock | `POST /external-task/{id}/extendLock` | `workerId`, `newDuration` (ms) |
| Unlock | `POST /external-task/{id}/unlock` | *(none)* |
| Liveness of engine | `GET /engine-rest/version` | — |

**Engine retry semantics (verified — decisive for §9).** In Camunda 7 / CIB Seven the engine **does not
auto-decrement retries**: the client sets `retries = fetchedTask.retries - 1` on `failure`. With
`retries > 0` and a `retryTimeout`, the task becomes fetchable again after that delay. When `retries`
reaches **0** the task is no longer fetchable and **the engine opens an incident** (surfaced to
operators / HITL). Lock expiry (no complete before `lockDuration`) also makes the task re-fetchable. First
delivery carries `retries = null` → the client treats it as the configured initial count.

## 5. External-task client / transport API

`WorkerTransport` (Protocol — the seam that makes the engine mockable in unit tests without faking it in
integration tests, ADR-0011):

```python
@runtime_checkable
class WorkerTransport(Protocol):
    async def fetch_and_lock(self, worker_id: str, topics: list[TopicSubscription],
                             *, max_tasks: int, async_response_timeout_ms: int) -> list[ExternalTask]: ...
    async def complete(self, task_id: str, worker_id: str, variables: dict[str, Any]) -> None: ...
    async def handle_failure(self, task_id: str, worker_id: str, *, error_message: str,
                             error_details: str = "", retries: int, retry_timeout_ms: int) -> None: ...
    async def handle_bpmn_error(self, task_id: str, worker_id: str, *, error_code: str,
                                error_message: str = "") -> None: ...
    async def extend_lock(self, task_id: str, worker_id: str, *, new_duration_ms: int) -> None: ...
    async def unlock(self, task_id: str) -> None: ...
    async def close(self) -> None: ...
```

`TopicSubscription = (topic_name: str, lock_duration_ms: int, variables: list[str] | None)`. `variables`
scopes which process vars the engine returns (least-privilege; PHI stays out of the general zone unless a
worker declares it). `CibSevenWorkerTransport.__init__(base_url, *, auth_token=None, timeout=20.0)`
builds one `httpx.AsyncClient(base_url=base_url.rstrip("/"), timeout=…)`; `auth_token` (blocked seam,
`deployment-worker-daemon.yaml:76-83`) adds `Authorization: Bearer …` only when present.

Response mapping (fetchAndLock item → `ExternalTask`): `id→task_id`, `topicName→topic`,
`processInstanceId`, `businessKey→business_key`, `retries` (kept for §9), `workerId`, and each
`variables[k]["value"]` flattened into `variables`. Camunda-typed output on `complete` via
`_to_camunda_var` (§ preserved from v1): `bool→Boolean`, `int→Integer` or **`Long`** when outside int32
(BRL cents / big ids, ADR-0018), `float→Double`, `dict|list→Json` (`json.dumps`), `None→String`,
pass-through when already `{"value": …}`. **This typing is load-bearing** — money and dossier round-trips
depend on `Long`/`Json`, and v1 fixtures assert it.

## 6. Long-poll loop with backoff + jitter

The loop uses engine **long-polling** (`asyncResponseTimeout` on `fetchAndLock`), not v1's client-side
`sleep` (v1 short-polled — donor `harness.py:407-425`). One iteration:

1. `topics = [(t, lock_duration_ms, vars_for(t)) for t in registry.list_topics()]`.
2. `tasks = await transport.fetch_and_lock(worker_id, topics, max_tasks=…,
   async_response_timeout_ms=…)` — the engine **holds the request** until a task is available or the
   timeout elapses. Requires `httpx` client timeout `>` `async_response_timeout_ms` (else the client
   aborts its own long-poll). Constraint enforced at settings load (§11): `client_timeout_s * 1000 >
   async_response_timeout_ms + slack`.
3. On tasks: `await asyncio.gather(*(self._handle(t) for t in tasks))`, then loop immediately (no sleep —
   there may be more work).
4. On **empty** result: short **idle backoff with full jitter** — `sleep(random.uniform(0,
   min(idle_base * 2**min(streak,k), idle_cap)))` — so N replicas don't re-poll in lockstep (thundering
   herd). With long-poll the common idle wait is already the engine timeout; this jitter only spaces
   reconnects.
5. On **transport error** (connect/5xx/timeout that isn't the long-poll's own): exponential backoff with
   full jitter (`base 1s → cap 30s`), increment `fetch_errors` metric, and after `≥ N` consecutive
   failures flip the readiness signal `engine_reachable=False` (→ `/readyz` 503, §12). The loop **never
   crashes** on a transient engine blip, but the failure is **never silently masked** — this is the
   fail-closed fix for v1's `except …: return []` swallow (donor `harness.py` fetch path).

Loop exits only on `asyncio.CancelledError` (drain, §8).

## 7. Topic routing via `WorkerRegistry` + the sync/async bridge

Dispatch is a pure lookup: `worker = registry.get(task.topic)`; unknown topic → log
`worker_unregistered` + report `handle_failure` with `retries=0` (fail-closed incident — a task with no
handler must not vanish; a human sees it). This can only happen if fetchAndLock subscribes a topic the
registry doesn't serve, which the readiness check (§12) forbids at boot.

`WorkerBase.run()` is **synchronous** by design (`base.py:52-55,107`; it `time.sleep`s between in-process
retries, `base.py:178`). The dispatch loop is async. Bridge: `result = await asyncio.to_thread(worker.run,
task.variables)` so a worker's blocking work (and any in-process sleep) never stalls the event loop or the
other tasks in the `gather`. Workers that need true async I/O override `run_async` (`base.py:194-206`);
the dispatcher prefers `run_async` when overridden, else `to_thread(run)`. The in-process retry budget
(`max_retries * retry_backoff * n`, default `3 × 1.0` ≈ 3s) **must** stay `< lock_duration_ms`; §9 pins
this and §11 validates it. Handlers must not exceed the lock — a `extend_lock` heartbeat is available for
the one known slow path (Rafael dossier / `auth_analyze`, called out in `deployment-worker-daemon.yaml:84`).

Handler outcome is **complete-exactly-once, by the dispatcher** (never the worker) — the worker returns a
`dict`; the dispatcher calls `complete`. This is why workers stay pure and idempotent.

## 8. Graceful shutdown (drain + explicit unlock)

On `SIGTERM`/`SIGINT` (installed via `loop.add_signal_handler`, uvicorn's own signal capture disabled so
the daemon owns the sequence):

1. Set `live=False` → `/healthz` returns 503 (k8s stops sending traffic to sibling HTTP surfaces; the
   engine is polled, so the effect is that no *new* `fetchAndLock` is issued).
2. **Stop fetching**: cancel the dispatcher task so no new tasks are locked.
3. **Drain in-flight**: await outstanding `_handle` coroutines up to a `drain_deadline_s` (must be `<`
   the pod `terminationGracePeriodSeconds`). Completed handlers `complete` normally.
4. **Explicit unlock** of anything still locked-but-not-completed at the deadline: track live task ids and
   `POST /external-task/{id}/unlock` each, so the engine can **immediately** re-deliver to a surviving
   replica. This is the deliberate improvement over v1, which relied solely on lock expiry (donor calls
   no `unlock`; the porter flagged the resulting `lock_duration_ms` re-delivery delay). Because handlers
   are idempotent and complete-once is dispatcher-owned, unlock-then-redeliver is safe.
5. Close transport, Kafka producer, OTel (`force_flush` + `shutdown`).

`WORKER_ID` is the pod `metadata.name` (Downward API, `deployment-worker-daemon.yaml:54-58`) — **unique
per replica** so two replicas never contend for the same lock. Drain correctness depends on this.

## 9. Error / retry / incident strategy — retry ownership (avoid double-retry)

This is the crux the charter flags. Three retry layers are *possible*; two of v1's overlapped and caused a
`3×3` multiplication plus a hardcoded-`retries=0` short-circuit (donor `harness.py`: tenacity
`stop_after_attempt(3)` around `_execute` **and** `WorkerFailureError.retries_left` ignored **and**
`max_retry_attempts` unwired). We collapse to a **single system of record**:

> **The engine owns durable retry/incident state. The dispatch loop owns NO retry. `WorkerBase.run()`
> in-process retry is scoped to "transient, idempotent, within-lock" and defaults to OFF (`max_retries=1`)
> on the engine-driven path.**

Mechanics:

- **Layer A — in-process (WorkerBase.run):** for the runtime path the dispatcher constructs/uses workers
  with **`max_retries=1`** (execute once; retry/metrics wrapper retained). A worker may **opt in** to a
  small in-process retry (`in_process_retries>1`) only for *provably idempotent* transient faults, and the
  budget must fit inside the lock (§7). Rationale: in-process retry hides failures from the engine's
  incident tooling and risks double side-effects on non-pure execute.
- **Layer B — engine (single source of truth):** when `execute` raises, the dispatcher classifies the
  exception and calls the engine:

  | Exception class (from workers) | Engine call | Retry? | Why |
  |---|---|---|---|
  | `ERR_*_NOT_HUMAN` guard / `*NotHumanError(PermissionError)` (e.g. `base.py:25-32`, `ans_submit.py:24`) | **`failure(retries=0)` → engine incident** (default) | **never** | Fail-closed escalation the engine **guarantees**: an incident is always created, always human-visible. Retrying an L0 guard could drive an adverse action — forbidden (ADR-0008). See the bpmnError hazard below. |
  | `WorkerBpmnError(error_code)` where `error_code` is **gate-proven modeled** (see hazard note) | `bpmnError(errorCode=…)` | **never** | Deterministic business outcome routed to a **modeled** error boundary → human gate in the process. Permitted only for proven codes. |
  | Validation errors — `*Invalido*Error(ValueError)` (e.g. `nip.py:40`, `contas.py:42`) | `failure(retries=0)` (default); `bpmnError` only if gate-proven modeled | **no** | Bad/immutable input won't fix itself on retry; route to incident/human. Per-topic `bpmnError` opt-in (§ open Q-3) is subject to the same gate. |
  | Transient / infra (`RuntimeError`, `httpx`/DB errors, `*RetryEsgotado*`) | `failure(retries = task.retries - 1, retryTimeout = jittered_backoff)` | **engine-side** | Re-delivered after backoff; at `retries==0` → engine incident (fail-closed, human-visible). |
  | Unknown/unclassified | `failure(retries = task.retries - 1, …)` | engine-side, but **alarm** | Default to durable retry, never silent-drop; emit `worker_unclassified_error`. |

  **The bpmnError silent-end hazard (live-proven on CIB Seven 2.1.0 — R1 verification).** A `bpmnError`
  whose `errorCode` has **no matching error boundary event** in the consuming BPMN does **not** open an
  incident: the engine silently **ends the process scope** — zero incidents, zero handlers, the case just
  stops. That makes `bpmnError` categorically **unsafe as a default** for L0 guards: an unmodeled
  `ERR_*_NOT_HUMAN` would silently drop the very case that must reach a human. The design default for
  guard escalation is therefore `failure(retries=0)` — the engine-guaranteed incident path — and
  `bpmnError` is a **per-code opt-in** allowed only where the boundary is proven to exist. **Design
  requirement (fail-closed gate):** a CI check *and* the runtime readiness check must verify that every
  `ERR_*` code a registered worker can emit as `WorkerBpmnError` has a matching error boundary (matching
  `errorCode`) in **every** BPMN under `spec/processes/bpmn/` that consumes that worker's topic; any
  unproven code is demoted to `failure(retries=0)` at dispatch (and fails the CI lane). The gate parses
  the spec BPMN XML (`bpmn:boundaryEvent` / `bpmn:errorEventDefinition` / `bpmn:error@errorCode`) — the
  same spec-as-truth posture as §12/Q-4.

  The dispatcher **reads `task.retries`** off the fetched task and decrements by 1 (engine does not
  auto-decrement, §2). First delivery (`retries=null`) → seed from `max_retry_attempts`
  (`WORKER_MAX_RETRY_ATTEMPTS`, §11) — which now **actually controls** engine retries (fixing v1's dead
  knob). `WorkerFailureError.retries_left`, when a worker raises it explicitly, is **honored** (overrides
  the computed value) — fixing v1's ignored field.

Net: exactly one retry counter (the engine's), one operator-visible backoff schedule, and incidents that
existing on-call/HITL tooling already understands. No path double-retries; no guard is ever retried into an
adverse action.

## 12. Health / readiness endpoints

A minimal health surface on `:8000` (Helm `containerPort: 8000`, `worker-daemon:90-113`):

- **`GET /healthz`** — liveness. 200 `{"status":"ok"}` while running; 503 `{"status":"shutting_down"}`
  during drain. Cheap, no dependency I/O (liveness must not depend on the engine).
- **`GET /readyz`** — readiness, runs checks concurrently, **fail-closed** (any check false → 503):
  - `engine_reachable` — last `fetchAndLock`/`GET /version` succeeded (or `< N` consecutive failures).
  - `workers_registered` — the registry serves **every** expected topic (`registry.list_topics()`
    superset of the spec's external-task topics). A missing worker → **not ready** (this is what prevents
    the §7 unknown-topic case at runtime).
  - `kafka_ready` — producer connected (only if Kafka publishing is enabled for this tenant).
- **`GET /metrics`** — Prometheus `generate_latest` (scraped via `podmonitor.yaml`; port named `metrics`).

Health-first ordering (Helm docstring `worker-daemon:10-11`): the HTTP server binds **before** the
engine/Kafka bring-up so `/healthz` is 200 immediately and slow deps don't trip the liveness probe;
`/readyz` stays 503 until the harness is genuinely serving all topics.

## 13. Metrics & mock boundaries

**Metrics** reuse the existing wiring — `WorkerBase.run()` already emits
`maezo_worker_execution_time_seconds{worker,topic}` and `maezo_worker_error_count_total{worker,topic,
error_type}` via `record_worker_execution`/`record_worker_error` (`observability.py:148-188`,
`metrics.py:54-67`). The dispatcher adds a **dispatch-outcome** metric expected by observability
(`podmonitor.yaml` "GAP-XOBS-4 dispatch-outcome"): `maezo_worker_task_total{tenant,topic,outcome}` with
`outcome ∈ {completed, bpmn_error, failed, incident}` plus a duration histogram, mirroring v1's
`maezo_worker_task_*`. Metric emission is best-effort and **never breaks dispatch** (as in

## 14. Test strategy & acceptance (T1.1)

Acceptance (plan §4, T1.1): *"Integration test: engine task → worker executes → completes/fails with
retry."* Concretely:

1. **Unit** (no engine): `FakeWorkerTransport` enqueues tasks; assert the dispatcher completes-once on
   success, **`failure(retries=0)` on guard error** (never retried; `bpmnError` only when the code is
   gate-proven modeled, and an unproven code demotes to `failure(retries=0)` — §9),
   `failure(retries=task.retries-1, retryTimeout>0)` on transient, and unlock-on-drain. Assert
   `WorkerBase.run` retry/metrics fire (labels correct).
   Plus the **boundary-proof gate test**: a `WorkerBpmnError` code with no matching
   `bpmn:error@errorCode` boundary in a consuming spec BPMN fails the CI check (mutation: strip a
   boundary → red).
2. **Settings** (fail-closed): a config with `async_response_timeout_ms ≥ client_timeout_s*1000` raises at
   startup; unknown-topic subscription fails readiness.
3. **Integration** (real CIB Seven `2.1.0` via `docker compose --profile core`): deploy one BPMN with an
   external task on topic T; start an instance; run the dispatcher; assert the engine history shows the
   external-task activity **ended** and the process advanced; force a transient failure and assert the
   engine re-delivers (`retries` decremented) then opens an **incident** at 0. This is the first member of
   the T3.1 port.
4. **Entrypoint smoke**: `python -m maezo.runtime.worker_runtime` boots, `/healthz` 200, `/readyz`
   reflects registry coverage; `python -m maezo.runtime.agent_runtime` boots health-only (no
   CrashLoopBackOff).

Author ≠ verifier (ground rule 2): R1 verification reproduces §3 independently against a fresh compose
engine.

## 18. Durable checkpoint persistence (T3.4/F4 — wired for real)

Closes the T3.4/F4 flag: *"PostgresSaver.setup() never called; `_load_agent_graph` passes no
checkpointer."* The LangGraph "working layer" (agent graph state) is now durably persistent.

**Where it wires.** `runtime/agent_runtime/service.py::_provision_checkpointer` runs once at
daemon bring-up (STEP B), constructs an `AsyncPostgresSaver` from the runtime's `DATABASE_URL`,
and calls `asetup()` once (idempotent). `_load_agent_graph` then builds the `Harness` WITH that
checkpointer and compiles the graph checkpoint-enabled. A new `checkpointer_ready` readiness
check surfaces the result.

**Async, not sync (proven).** Graph execution is `ainvoke`; the sync `PostgresSaver`'s async
methods raise `NotImplementedError`, so wiring uses `AsyncPostgresSaver`. Verified round-trip
(setup/put/get/list/delete) against **langgraph 1.2.9 + langgraph-checkpoint 4.1.1 +
langgraph-checkpoint-postgres 3.0.5** on real Postgres 16.

**Fail-closed discipline (F2).** `agent_runtime_mode != "local"` is production. There, a missing
`DATABASE_URL` or an `asetup()`/connect failure leaves `checkpointer_ready` **RED** — the daemon
refuses to advertise readiness rather than silently run stateless (no resume-after-restart).
Local/dev falls back to an in-memory saver with a **loud warning** (state does not survive
restart — dev ergonomics only). Mirrors the a2a card-signing (§6.2 of the A2A design) and
`worker_runtime` `audit_sink_ready` postures.

**Why `asetup()`, not Alembic.** The four real tables (`checkpoints`, `checkpoint_blobs`,
`checkpoint_writes`, `checkpoint_migrations`) are an **upstream-owned schema** — the saver's own
`MIGRATIONS` list, versioned by its `checkpoint_migrations` bookkeeping table. Mirroring that DDL
into Alembic would fork the schema and drift on every library bump. Full rationale:
`platform/migrations/versions/0006_retire_dead_checkpoint_tables.py`.

**Thread-id / PHI discipline.** `checkpoint_blobs` stores BYTEA channel values that ARE
PHI-bearing, keyed by `thread_id`. Thread ids therefore MUST NOT embed a raw identifier — the
convention is the hashed `wa:{tenant}:{phone_hash}` conversation id (`webhooks/whatsapp/
dispatch.py`) or the `ESC-{tenant}-{conversation_id}` process business key (`agents/helena/
graph.py`). `runtime/checkpoint.py::checkpoint_thread_config` builds the config and fail-closes on
an obviously-raw-numeric id (`assert_phi_safe_thread_id`).

**LGPD / erasure obligation (now REAL).** Persistence previously existed nowhere in prod bootstrap,
so `platform/erasure.py`'s checkpoint-erasure docstrings (corrected in T3.4/F4 to name the four
real tables) described a purely hypothetical surface. **This wiring makes those tables real
PHI-bearing stores.** Retention/erasure remains **DPO-gated and fail-closed** — T3.4/F3's
`ErasureManager` still raises `ErasureNotImplementedError` rather than certify a layer clean
without a real `SELECT`, and that fail-closed shape STANDS (this change does not implement
erasure). The standing obligation: a real working-layer erasure must `DELETE FROM checkpoints /
checkpoint_blobs / checkpoint_writes WHERE thread_id = ANY(...)`, which requires a
`thread_id → fhir_patient_id` mapping (checkpoints are keyed by `thread_id`, not patient id — the
caveat already documented in `erasure.py::_erase_working`). Until that mapping and a DPO-approved
job exist, working-layer erasure stays fail-closed.
