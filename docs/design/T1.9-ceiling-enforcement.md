# Design T1.9 — Ceiling enforcement (remove `dentro_teto` bypass; port v1 `ceilings.py`)

Status: Proposed (pending implementation T1.9).
Owner: policy-guardian. Defect: B3/B4 family (decorative ceiling / manufactured `dentro_teto_l2`).
Depends on T1.8 (PEP `load_matrix`) and T0.3. Port source: v1 `tools/workers/ceilings.py`.

Zero-trust: all mechanics below cite actual code lines verified this session. D-07 ceiling values are
`blocked(external: diretoria AMH)`; the design must work with the placeholder `max_value_brl: 0`
(= everything routes to human review) until they are provided.

## 1. The bypass, exactly (current data flow that manufactures `dentro_teto_l2`)

### 1.1 reembolso.py:227-230 — the manufacture
`src/maezo/tools/workers/reembolso.py`, `calculate_value` (reembolso.py:203-246):
```
226   dentro_tabela = input_data.valor_solicitado_cents <= valor_calculado
227   dentro_teto = input_data.dentro_teto_l2          # <-- echoes the INBOUND boolean
228
229   if dentro_tabela and valor_calculado > 0:
230       dentro_teto = True   # <-- MANUFACTURES within-ceiling from within-table alone
```
Two independent defects on this path:
- **Echo-through (line 227):** `dentro_teto` is seeded from `input_data.dentro_teto_l2`
  (`ReembolsoInput.dentro_teto_l2`, reembolso.py:78) — a caller-supplied boolean. Any upstream that sets
  `dentro_teto_l2=True` is trusted verbatim. No ceiling is ever read.
- **Manufacture (line 229-230):** even if the inbound were False, being *within the reference table* and
  `valor_calculado > 0` flips `dentro_teto = True`. So "within table" is silently equated to "within the
  tenant's L2 auto-approval ceiling" — two different governance facts. There is **no** read of
  `reembolso_auto_approval.max_value_brl` anywhere (grep `max_value_brl` over `src/`: **zero** Python hits;
  only YAML + a comment). The ceiling is decorative.

The manufactured value flows into `ReembolsoCalculoResult.dentro_teto_l2` (reembolso.py:236) and then into
the auto-approval gate `auto_approve_or_route` (reembolso.py:267):
```
267   if calculo.dentro_tabela and calculo.dentro_teto_l2 and not requer_avaliacao_clinica:
268       recomendacao = "AUTO_APROVAR"
```
→ A within-table reimbursement auto-approves with **no** ceiling check, regardless of tenant governance or
the `max_value_brl: 0` D-07 placeholder. This is the core L0/financial defect.

The BPMN documentation *claims* the worker "COMPUTA dentro_teto_l2 (comparando o mesmo valor de referencia
vs teto do tenant)" (`SP-OP-REEMBOLSO-001_...bpmn:209`) and L0-core.yaml:28 *claims* the worker "compara …
com este teto (via gateway.pep.load_matrix) e COMPUTA dentro_teto_l2 — nunca confia no booleano de entrada."
**Both are comment-only aspirations; the code does the opposite** (reembolso.py:227-230). Classic
zero-trust trap — the design must make the comments true.

### 1.2 auth.py:66 — same class of bypass (echo-through)
`src/maezo/tools/workers/auth.py`, `AnalyzeRequestWorker.execute`:
```
66    teto_ok = process_vars.get("dentro_teto_l2", False)   # <-- echoes inbound; never computed
...
75    if all([dut_ok, teto_ok, rede_ok, beneficiario_ativo, carencia_ok, docs_completa]):
...        return {"status": "auto_approved", "recommendation": "AUTO_APROVAR", ...}
```
`dentro_teto_l2` is read straight off `process_vars` and fed into the L2 auto-approval `all([...])` gate
(auth.py:75-88). Same defect class as reembolso: an upstream seeding `dentro_teto_l2=True` auto-approves an
authorization with no ceiling read. AUTH carries the value needed to recompute it: the process contract
lists `valor_estimado_brl` as an input variable (`SP-OP-AUTH-001_...bpmn:59`), and v1's auth worker uses
exactly that (v1 auth_analyze.py:225 `round(float(state["valor_estimado_brl"])*100)`).

### 1.3 mcp_dmn/server.py:51 — echo-through, but the DMN is the WRONG place to fix it
`src/maezo/tools/mcp_dmn/server.py:51` is a **docstring** line: the usage example
`server.evaluate_decision("auth_auto_approval", {"dut_atendida": True, "dentro_teto_l2": True})`
(server.py:49-53). It is not runtime logic. The real behavior: `evaluate_decision` (server.py:93-205) is a
faithful DMN 1.3 evaluator — it matches whatever `inputs` dict it is given (server.py:158-201) and, for
`auth_auto_approval.dmn` rule r1 (`dut_atendida=true, dentro_teto_l2=true, rede_credenciada=true →
AUTO_APROVAR`, auth_auto_approval.dmn:34-42), it will output AUTO_APROVAR whenever it is *handed*
`dentro_teto_l2=true`. So the DMN **echoes through** any `dentro_teto_l2` it receives.

**This is correct and must NOT change.** Per ADR-0012 the DMN is the sole rule source and a **pure
evaluator of facts**; `dentro_teto_l2` is a *fact* that must be COMPUTED by the worker *before* the DMN is
consulted. Fixing the ceiling inside the DMN engine would put a business threshold in the wrong layer and
duplicate the rule. The DMN legitimately consumes `dentro_teto_l2`; it must never **originate** it. The
enforcement therefore lives in the worker (which computes the fact), and defense-in-depth is provided by the
architecture test in §5 ("no code path sets `dentro_teto_l2` except the ceiling resolver") + the PEP.
Note the v2 mcp_dmn tests seed `dentro_teto_l2=True` directly (test_mcp_dmn.py:48,70) — that is fine for a
DMN unit test (it tests the evaluator in isolation); it is not a bypass of the *worker* path.

### 1.4 (adjacent, same family) pagto.py:123 — echo-through in payments
Out of T1.9 scope but same defect and same fix: `src/maezo/tools/workers/pagto.py:123`
`dentro_teto = variables.get("dentro_teto_l2", False)` then `if valor_cents <= 10_000_000 and dentro_teto`
(pagto.py:126 — a **hard-coded** R$100k literal, not the policy `high_value_payment.threshold_brl`). Flag
for a sibling task; the ported `CeilingResolver` serves it (v1 pagto.py:528-531 uses
`action="high_value_payment", param="threshold_brl"`, v1 pagto.py:173-174).

## 2. v1 `ceilings.py` port plan

### 2.1 What v1 `CeilingResolver` does (verified, v1 ceilings.py:1-133)
- Loads the **same** autonomy matrix the PEP evaluates via `gateway.pep.load_matrix` (L0-core + tenant
  overlay) — v1 ceilings.py:35, 45-63. One source of truth for ceilings and for PEP decisions.
- `ceiling_brl(tenant, action, param)` (v1 ceilings.py:97-119): resolves `action.params[param]` to a whole-BRL
  int; **fail-closed to 0** when the matrix is unloadable, the action is absent, the param is absent,
  non-numeric, a bool (bool-is-int trap explicitly rejected, v1 ceilings.py:110-111), or **negative**
  (clamped to 0, v1 ceilings.py:117).
- `within_l2_ceiling(tenant, action, param, value_cents)` (v1 ceilings.py:121-132): returns
  `value_cents <= ceiling_brl * 100` (inclusive at the ceiling), **except** ceiling 0 → **always False**
  (v1 ceilings.py:130-131). Ceiling 0 is the D-07 state: nothing auto-approves. Money is centavos-int
  (arbitrary precision; no float, ADR-0018).
- Matrix load is cached by (core_path, overlay_path, tenant) with `@lru_cache` and swallows load errors to
  `None` → ceiling 0 → False (v1 ceilings.py:45-63). A broken/missing config **never** auto-approves.
- Overlay auto-discovery: `<core-dir>/tenants-<tenant>.yaml` per-tenant (v1 ceilings.py:86-91).

### 2.2 What adapts for v2
- **Import path / matrix API**: depends on T1.8 porting `load_matrix` + `AutonomyMatrix`/`ActionPolicy`
  into v2 `gateway/pep.py`. `CeilingResolver` imports `from maezo.gateway.pep import AutonomyMatrix,
  load_matrix` (v1 ceilings.py:35) — works unchanged once T1.8 lands. **Hard dependency: T1.9 cannot land
  before T1.8.**
- **Default core path** (RATIFIED 2026-07-16, T1.8/D2 option (b)): policies stay canonical at
  `spec/policies/autonomy/`. v1's `_DEFAULT_CORE_PATH = "src/maezo/policies/autonomy/L0-core.yaml"`
  (v1 ceilings.py:42) does NOT carry over. The v2 resolver default MUST be derived via T0.3's
  `resolve_spec_dir()`/`MAEZO_SPEC_DIR` mechanism (landing in `src/maezo/agents/__init__.py`; not yet on
  main this session): `resolve_spec_dir() / "policies" / "autonomy" / "L0-core.yaml"` — the same
  resolution the PEP factory uses, never a second scheme. Packaging note: the wheel ships only `src/maezo`
  (`pyproject.toml:61-62`), so T1.8/D2's hatch force-include of `spec/policies/autonomy/*.yaml` is a
  prerequisite for the resolver working in a packaged deployment (until then, an unloadable matrix
  fail-closes to ceiling 0 — safe but everything routes to human). `AUTONOMY_CORE_PATH` may remain only
  as a narrow test-pinning override (v1 ceilings.py:81 precedent).
- **Worker wiring style differs**: v1 workers are async external-task handlers with Kafka/harness
  (v1 reembolso.py `make_calculate_amount_handler`, v1 reembolso.py:427-520; v1 auth_analyze.py:234-268).
  v2 workers are **plain synchronous functions** (`calculate_value(input_data) -> ReembolsoCalculoResult`,
  reembolso.py:203) and `WorkerBase.execute(process_vars) -> dict` (auth.py:50). So the port adapts the
  *call sites*, not the resolver: instantiate `CeilingResolver` once (module-level or injected) and call
  `within_l2_ceiling(...)` from the sync function.
- **Target module path**: `src/maezo/tools/workers/ceilings.py` (mirrors v1). Copy v1 `ceilings.py`
  verbatim except the default path constant. Port v1 `tests/unit/tools/workers/test_ceilings.py`
  (test_ceilings.py:1-167) wholesale — its hand-written fixtures already require all 5 hard actions present
  (test_ceilings.py:21-27, matching T1.8's English hard set), so it doubles as a T1.8/T1.9 integration check.

### 2.3 How `max_value_brl` flows from policy → runtime DENY (reembolso)
Target `calculate_value` (replacing reembolso.py:227-230):
```
# module scope
_CEILING_ACTION = "reembolso_auto_approval"   # matches L0-core.yaml:24
_CEILING_PARAM  = "max_value_brl"
_resolver = CeilingResolver()                  # or injected for tests (see §2.4)

# inside calculate_value(input_data):
valor_calculado = _lookup_tabela_referencia(...)          # reembolso.py:219 (see docs/review-queue.md M-2)
dentro_tabela   = input_data.valor_solicitado_cents <= valor_calculado   # reembolso.py:226 (unchanged)
# REMOVE reembolso.py:227-230 entirely. COMPUTE the ceiling fact — never trust input_data.dentro_teto_l2:
dentro_teto = _resolver.within_l2_ceiling(
    tenant=input_data.tenant_id,                         # ReembolsoInput.tenant_id (reembolso.py:59)
    action=_CEILING_ACTION, param=_CEILING_PARAM,
    value_cents=valor_calculado,                         # reference-table value in centavos (per L0-core.yaml:28)
)
```
Flow end-to-end with the D-07 placeholder:
`L0-core.yaml:24 reembolso_auto_approval.max_value_brl: 0` (+ `tenants-amh.yaml:8-9` overlay also 0) →
`ceiling_brl → 0` → `within_l2_ceiling → False` (v1 ceilings.py:130-131) → `ReembolsoCalculoResult
.dentro_teto_l2 = False` → `auto_approve_or_route` gate (reembolso.py:267) `dentro_teto_l2` is False →
`recomendacao = "ANALISE_HUMANA"` (reembolso.py:271, motivo "Valor acima do teto de auto-aprovacao L2",
reembolso.py:276-277). **Every reimbursement routes to human review until diretoria sets a real ceiling.**
When diretoria provides `max_value_brl = N`, only `valor_calculado <= N*100` auto-approves; the code path
does not change (values are config, not code).

### 2.4 How `max_value_brl` flows → runtime DENY (auth)
Target `AnalyzeRequestWorker.execute` (replacing the echo at auth.py:66). MANDATE (adversarial-verifier
confirmed v2 never reads `valor_estimado_brl` today and its runtime population is statically unprovable):
**missing/None/non-numeric `valor_estimado_brl` → `teto_ok = False`** (route to human). NEVER
default-to-0-and-pass — with a positive ceiling configured, a defaulted 0 would read as "within ceiling",
which is fail-OPEN. This is an **intentional hardening divergence from v1**: v1 `_as_float` defaults
missing/invalid to `0.0` (v1 auth_analyze.py:135-142, used at :225) — do NOT port that default.
```
_CEILING_ACTION = "authorization_approval"     # L0-core.yaml:22
_CEILING_PARAM  = "max_value_brl"
# inside execute(process_vars):
raw_valor = process_vars.get("valor_estimado_brl")
try:
    valor_cents = round(float(raw_valor) * 100) if raw_valor is not None else None
except (TypeError, ValueError):
    valor_cents = None
if valor_cents is None:
    teto_ok = False        # FAIL-CLOSED: value absent/unparseable -> never within ceiling -> human review
else:
    teto_ok = self._resolver.within_l2_ceiling(
        tenant=process_vars.get("tenant_id", ""), action=_CEILING_ACTION,
        param=_CEILING_PARAM, value_cents=valor_cents,
    )
# IGNORE process_vars["dentro_teto_l2"] entirely
```
Then the existing `all([dut_ok, teto_ok, rede_ok, ...])` gate (auth.py:75) uses the computed `teto_ok`.
Same D-07 behavior: ceiling 0 → `teto_ok=False` → never `auto_approved` → dossier to Rafael (auth.py:99-105).
The worker should also **write the recomputed `dentro_teto_l2` back** into its return dict so the DMN
`auth_auto_approval` (which reads `dentro_teto_l2`, auth_auto_approval.dmn:23-24) receives the computed
fact, never the inbound one — mirrors v1 (`state["dentro_teto_l2"] = _resolve_dentro_teto_l2(...)`,
v1 auth_analyze.py:268).

Resolver injection: give both workers an optional `resolver: CeilingResolver | None = None` param
(default constructs one), exactly as v1 (`make_calculate_amount_handler(..., resolver=None)`,
v1 reembolso.py:427; `make_analyze_request_handler(..., resolver=None)`, v1 auth_analyze.py:239) so tests
can pin a synthetic core/overlay via `CeilingResolver(core_path=...)`.

### 2.5 Enforcement-point decision: **worker computes the fact; PEP + architecture test are defense-in-depth**
Recommendation: **compute `dentro_teto_l2` in the worker** (the layer that already owns the arithmetic and
has `valor`/`tenant`), feed the computed fact to the DMN, and additionally rely on:
- **PEP** (T1.8) as the coarse gate: `authorization_approval`/`reembolso_auto_approval` are L2 with a
  `max_value_brl` param the PEP now loads; the PEP can (future) refuse an L2 auto-approval whose value
  exceeds the ceiling. But the PEP evaluates *actions*, not per-request *values* today (v1 pep evaluate
  takes no value) — so the PEP alone cannot enforce the ceiling; it needs the resolver at the worker. Hence
  **both**, not PEP-only.
- **DMN** stays a pure evaluator (§1.3) — not an enforcement point for the ceiling, only a consumer of the
  computed fact.
- **Architecture test** (§5) freezes the invariant that no worker line assigns `dentro_teto_l2` from
  anything but the resolver. This is what makes "worker computes it" trustworthy rather than
  comment-deep.

Why not DMN-only or PEP-only: DMN-only would embed a business threshold in the rule table and still trust
an inbound fact (the exact current bug); PEP-only cannot see the request value. Worker-computes-fact +
resolver-reads-policy is the v1-proven design and the one L0-core.yaml:28 already prescribes.

## 3. Fail-closed invariants (constraint 2) preserved by the port
- Ceiling absent / 0 / negative / non-numeric / bool / matrix unloadable → `within_l2_ceiling = False`
  (v1 ceilings.py:104-131). Nothing auto-approves on a config problem.
- The reference value fed to the resolver is the **computed table value** (`valor_calculado`), and if the
  table returns 0 (`SEM_TABELA` catch-all, reembolso_calculo.dmn:72-79 → 0) then `dentro_tabela=False`
  anyway → ANALISE_HUMANA. Out-of-table never auto-approves (reembolso.py:274-275).
- Inbound `dentro_teto_l2` / `input_data.dentro_teto_l2` is **never read** on the decision path after the
  port. (Field may remain on the dataclass for wire-compat but must be ignored — architecture test guards
  this.)

## 4. D-07 status: blocked(external)
`reembolso_auto_approval.max_value_brl` and `authorization_approval.max_value_brl` are **0** in both
`L0-core.yaml:22,24` and `tenants-amh.yaml:7,9`, annotated "D-07 em aberto: definir teto … com diretoria
AMH". These are **blocked(external: diretoria AMH)** — real numbers are a governance decision, not an
engineering one. The design is complete and correct with the placeholder: `0 → False → everything to human
review` (the safest possible default). When diretoria provides values, they are edited into
`tenants-amh.yaml` (overlay refines params — allowed for non-hard L2, v1 pep.py:262-266); **no code change**.
Do NOT fabricate a ceiling value to make auto-approval "work" in a demo (constraint 3).

5a. `test_auth_absent_valor_estimado_fails_closed` (**mandated by Rev 4**): resolver pinned to a
   **positive** ceiling (e.g. `max_value_brl: 500`), `process_vars` with all other auto-approve facts True
   but `valor_estimado_brl` **absent** (and variants: `None`, non-numeric string) →
   `execute(...)["status"] != "auto_approved"`. Proves missing value never defaults to 0-and-pass (§2.4
   mandate; intentional divergence from v1 `_as_float` default-0.0, v1 auth_analyze.py:135-142).
6. `test_no_code_path_sets_dentro_teto_l2_except_resolver` (**architecture test**, port the AST-scan idea
   from v1 `test_pep_bypass.py:224` `test_no_module_invokes_tool_handlers_directly`): parse
   `reembolso.py`, `auth.py`, `pagto.py` with `ast`. The rule flags only assignments/dict-values that
   **ORIGINATE** the ceiling fact from an untrusted source, and permits **propagation** of an
   already-resolver-derived value. Precisely, for names in {`dentro_teto`, `dentro_teto_l2`, `teto_ok`}:
   - **FORBIDDEN (origination)**: RHS is a bare constant `True` (e.g. today's `dentro_teto = True`,
     reembolso.py:230); RHS reads the inbound payload — `process_vars.get("dentro_teto_l2", ...)`
     (today's auth.py:66), `variables.get("dentro_teto_l2", ...)` (pagto.py:123), or an
     `input_data.dentro_teto_l2` attribute read (today's reembolso.py:227); RHS is any boolean
     expression derived from non-resolver facts (e.g. `dentro_tabela and ...`).
   - **PERMITTED (propagation / declaration)**: RHS is a call to `CeilingResolver.within_l2_ceiling`
     (or the local name bound to it), including via the `valor_cents is None → False` fail-closed guard
     of §2.4; forwarding a variable that was itself assigned from the resolver into a result object or
     dict (e.g. `dentro_teto_l2=dentro_teto` at the `ReembolsoCalculoResult` construction,
     reembolso.py:236, and the worker return dict); and dataclass **field defaults**
     (`dentro_teto_l2: bool = False`, reembolso.py:78 and :102 — declarations, not decisions).
   This is the "no code path can set `dentro_teto_l2=True` except policy" test (T1.9 criterion). Under
   this refined rule it still **fails today** against reembolso.py:227, reembolso.py:230, auth.py:66 and
   pagto.py:123 (proving it bites) and passes after the port **without** false-positives on the legit
   propagation at reembolso.py:236 or the field defaults at reembolso.py:78/:102.
7. `test_ceiling_action_names_exist_in_matrix`: assert `_CEILING_ACTION` constants
   (`reembolso_auto_approval`, `authorization_approval`, and for pagto `high_value_payment`) each resolve in
   the real matrix with the expected `param` key — catches a rename drift between worker constants and YAML.
8. `test_overlay_unknown_action_fails_closed_in_resolver`: a `tenants-<t>.yaml` overlay whose `overrides`
   references an action absent from the core → `load_matrix` raises `PolicyError`
   (v1 pep.py:238-239) → `_load_matrix_cached` swallows to `None` (v1 ceilings.py:55-63) → resolver
   `within_l2_ceiling(...) is False` for **every** action of that tenant. Note the dual semantics by
   layer: the PEP factory (T1.8) refuses to start on this same input (docs/adr/0025-pep-policy-unification.md §4 test 12); the resolver
   fail-closes to deny-auto-approval. Both are fail-closed; neither warns-and-passes.
