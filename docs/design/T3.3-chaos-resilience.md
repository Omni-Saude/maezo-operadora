## 0. Executive summary (the honest ground truth)

The single most important recon finding is that **the system has TWO distinct cross-process
handoff mechanisms, and only ONE of them is real, fenced, idempotent, audited, and testable
today:**

1. **Fenced worker/agent starts through `start_process_idempotent`** — the SOLE ADR-0007-audited,
   business-key-idempotent process-start chokepoint (`src/maezo/tools/mcp_cibseven/transport.py:560`).
   Emit-durable-audit-BEFORE-engine-effect; `find_active_instance` idempotency; dedup key
   `{tenant}:start:{process_key}:{business_key}` (`transport.py:549`, `595-622`).
   - **INADIMPLENCIA→CANCEL** (`inadimplencia.handoff_rescisao`, `src/maezo/tools/workers/inadimplencia.py:492`)
     is the ONE real cross-process worker handoff. Already integration-tested with a live engine +
     live Postgres + the anti-dupla GAP-INAD-1 proof (#93/#108) in
     `tests/integration/processes/test_sp_op_inadimplencia_001.py`.
   - Each **agent's own process start** is fenced+idempotent+audited: rafael→AUTH-001
     (`agents/rafael/graph.py:493`), helena/lucas→ESCALATION-001 (`agents/helena/graph.py:675`,
     `agents/lucas/graph.py:641`), gustavo→ANS-SUBMIT/NIP (`agents/gustavo/graph.py:697`),
     fernando→INADIMPLENCIA, valentina→PROGRAMA, marina→CONTAS/RECURSO (`agents/marina/graph.py:706`),
     andre→PAGTO, carolina→CRED.

2. **Event-driven `NotificationBridge` choreography** (`src/maezo/platform/notification_bridge.py`)
   — the *intended* transport for CONTAS→RECURSO, CONTAS→FRAUDE, FRAUDE→{CRED,CANCEL,INADIMPLENCIA}.
   **This is UNWIRED and FAIL-OPEN:**
   - Default starter is `_noop_starter` returning a placeholder id (`notification_bridge.py:103,377-379`).
   - `execute_handoff` catches **all** exceptions and only logs (`notification_bridge.py:291-307`) —
     a failed handoff is swallowed, never retried, never an incident (**fail-open**).
   - The starter signature is `(process_key, variables)` — **no business_key, no `audit_sink`, no
     `AgentDecisionProvenance`** — so it structurally **bypasses the fenced chokepoint**: no
     ADR-0007 audit, no `find_active_instance` idempotency, no anti-dupla guarantee.
   - The class has **no `__main__`/`main`** and is constructed **only in tests**
     (`grep NotificationBridge( src` → only `tests/`). No Kafka consumer wires `on_event`.
   - The Helm `deployment-bridge.yaml:50` runs `python -m maezo.platform.integrations.notifications_bridge`
     — **that module does not exist** (`src/maezo/platform/integrations/` is absent). Same for
     `consent_revocation_bridge` / `network_change_bridge`. These are dangling entrypoints (same
     class of gap as the removed tasy-simulator).
   - The worker-side "handoffs" `fraude.start_credenciamento` / `fraude.start_contratual`
     (`workers/fraude.py:615,636`) and `nip.handoff_ans_submit` (`workers/nip.py:241`) are
     **payload-shaping stubs** that return dicts — they do **not** start any downstream process.

**Consequence for T3.3:** The **CONTAS→RECURSO→FRAUDE** chain the plan names as a chaos target is
**not wired** — it cannot be chaos-tested end-to-end because the choreography does not run. This is
a **build dependency (wire the bridge through the fenced chokepoint), not a test gap**. The chaos
wave must NOT design fiction against it. The honest T3.3 deliverable is:
- BUILD-NOW chaos suites against the **real** fenced chain (INADIMPLENCIA→CANCEL + agent own-starts)
  and the **real** fail-closed audit surfaces (already precedented by the T-E sink-down drill).
- A **negative-certification guard** that pins the bridge's current fail-open status so no false L0
  claim is made, plus a prerequisite build task to wire it before its chaos suites can exist.
- An honest **external-blocker** boundary for true network-partition and DB-failover (need infra the
  lean single-PG CI stack cannot provide).

**Transport of the real path:** `start_process_idempotent(transport, process_key, business_key,
variables, audit_sink, provenance)` (`transport.py:560`). Fail-closed ordering: (1) `emit_once`
durable ADR-0007 record BEFORE effect (`:599`), (2) `find_active_instance` idempotency hit returns
existing unchanged (`:604-612`), (3) else `start_process_instance` (`:615`). `audit_sink`/`provenance`
are REQUIRED (no defaults) so an un-audited start is a call-time `TypeError`.

**Business-key correlation:** deterministic function of process vars (no wall-clock/uuid) —
CANCEL key `CANCEL-{tenant}-{numero_contrato}` (`inadimplencia.py:_cancel_business_key`),
FRAUDE key `FRAUDE-{tenant}-{numero_caso}` (`agents/beatriz/graph.py:201`), ESCALATION key per
contract. Re-run keys the SAME instance → emit dedups to the same chain link.

**Already tested (cross-process):** only `test_sp_op_inadimplencia_001.py` (INADIMPLENCIA→CANCEL
handoff + anti-dupla). `test_sp_op_cancel_001.py` covers CANCEL idempotency. No `tests/**` matches
`chaos|pod.kill|partition|failover|crash|restart`.

### 1.2 Resilience surfaces (fail-closed points the chaos suite must exercise)

- **Durable audit is crash-atomic.** `PostgresAuditSink.emit_once` runs the dedup-claim + chain-link
  INSERT inside ONE per-tenant `pg_advisory_xact_lock` transaction (`audit_postgres.py:337-345`,
  `_ADVISORY_LOCK_SQL:137`, `_DEDUP_CLAIM:148`). Its docstring states the target invariant verbatim:
  *"Crash between claim and chain-insert → both roll back together … This is the property the
  kill-test proves"* (`audit_postgres.py:310-313`). **This is the seam B1 must prove.**
- **`verify_chain(dsn, tenant_id)`** (`audit_postgres.py:530`) recomputes the hash chain from genesis
  and detects tamper + gap/fork — the ideal **post-crash assertion oracle** (no torn/orphan rows).
- **Emit-before-effect fence** (`transport.py:595-615`): a durable row always precedes an engine
  start; `AuditPersistenceError` propagates (neither a `CibSevenError` nor caught) → the turn fails,
  no start. This is the fail-closed direction a chaos test must NOT be able to invert.
- **Cross-loop seams (why per-call clients exist):** `FreshClientCibSevenTransport`
  (`workers/cibseven_engine.py:52`) and `FreshSinkAuditEmitter` (`audit_postgres.py:453`) build a
  fresh `httpx.AsyncClient` / `PostgresAuditSink` **inside each call's `asyncio.run` loop** because a
  pooled client bound to a dead loop dies with `RuntimeError: Event loop is closed`
  (`cibseven_engine.py:8-31`). Both are **fail-closed** (emit failures propagate as
  `AuditPersistenceError`, `audit_postgres.py:466-469`). A chaos suite that restarts the worker must
  confirm these seams survive loop churn (they already do by construction).
- **Worker-daemon readiness gate (T-D, `audit_sink_ready`)** (`runtime/worker_runtime/service.py:373-402`):
  `/readyz` stays RED and the daemon **never enters the fetch-and-lock rotation** unless a bounded
  live probe proves the sink can reach `audit_chain` (`:466-474`, `_bring_up_dependencies`). No
  `DATABASE_URL` → no sink → **no harness built → daemon never serves** (`:459-462`, `486`). This is
  the fail-closed startup a **worker-daemon restart** chaos suite exercises.
- **Idempotency / anti-dupla double-effect window (the real risk).** Engine-side start is **not**
  business-key-unique in CIB Seven; idempotency comes ENTIRELY from the query-then-act
  `find_active_instance` → `GET /process-instance?businessKey=X&active=true` then start
  (`transport.py:206-210`, `604-615`) — a **TOCTOU**. `emit_once` dedups the AUDIT row but does NOT
  gate the second START. Under crash-restart the external-task **lock** (`lock_duration_ms`) is the
  only serializer of re-delivery; if the lock expires mid-flight and two workers fetch the same task
  concurrently, both can see `find_active_instance == None` and **double-start**. **This is the
  precise invariant the crash suite must prove holds (and the honest risk to surface).**

### 1.3 Test-infrastructure reality (what CI can actually run)

- CI `integration` job (`.github/workflows/ci.yml`): `docker compose --profile core up -d` →
  **postgres (single, `pgvector/pgvector:pg16`), cibseven 2.1.0, hapi-fhir, kafka** on
  `ubuntu-latest`; waits for health; `make test-integration` (= `pytest tests/integration -q -m
  integration`); `docker compose --profile core down -v`. `MAEZO_PG_HOST_PORT=5432`.
- Real engine + **real Postgres** + **real alembic migrations** per-run tenant schema
  (`tests/integration/conftest.py:191-260`); `audit_sink` fixture is a real `PostgresAuditSink`,
  function-scoped for loop-safety (`:263-279`). Engine/PG unreachable → **loud explicit skip**, never
  a silent pass (ADR-0011; `conftest.py:46-54`, `227-232`).
- **`testcontainers>=4.0,<5.0` is already a dev dependency** (`pyproject.toml:62`, `uv.lock:2295`).
  This is the controllable-container harness that WOULD run true crash/restart suites (per-test
  isolated postgres/cibseven the test can start/stop/pause/kill) — **it is available**, just unused.
- Tests already shell to `docker compose -p <proj> up/down` for isolated PG stacks
  (`tests/unit/runtime/test_worker_runtime_audit_sink_pg.py:14`, `test_harness_audit_integration.py:95`),
  and `test_sp_op_cancel_001.py:66` documents live proof on a fresh `docker compose -p cancelfix`
  stack. So **container control from the test process is an established pattern**.
- **What is NOT CI-runnable:** the lean stack is **single-PG** — no replica, no Patroni/Aurora HA. A
  true **DB-failover** (primary down → replica promotion → app reconnects) has no topology to fail
  over to. A true **network partition** needs a `toxiproxy`/`pumba` sidecar not present in the stack
  or deps. Both are **external blockers**; their *fail-closed-on-loss* halves ARE runnable (see §2).

### 1.4 Anti-dupla / L0 interaction

The #108 anti-dupla proof (`test_sp_op_inadimplencia_001.py:791+`) shows `resolve_facts` refuses a
suspension when a CANCEL-001 is active for the same contract (`_query_ja_em_rescisao_cancel` →
`find_active_instance`). Chaos MUST NOT manufacture a false L0 guarantee: a pod-kill mid-handoff
could create a duplicate CANCEL instance (the §1.2 TOCTOU) which would then make the anti-dupla
guard trivially "pass" while actually two terminals exist. The crash suite's job is to prove
**convergence to exactly one CANCEL + exactly one audit chain link** after crash-restart, and that
the anti-dupla guard remains causally decisive (not vacuously true).

| **B3** | Engine restart mid-flight | `docker restart cibseven` with a task locked | external-task lock expiry → re-delivery → idempotent convergence; no lost task, no double effect | task completes once post-restart; `verify_chain` valid | 🟡 (slow, 90s boot) |

### Class C — Infra failure (partition / failover)

| ID | Scenario | Injection | Fail-closed invariant proven | Pass criterion | CI? |
|----|----------|-----------|------------------------------|----------------|-----|
| **C1-down** | Audit-sink / PG **down** (fail-closed half) | pause/kill postgres during a completion + a handoff start | `AuditPersistenceError` propagates → task retries → incident; NEVER an un-audited effect | no completion/start without a preceding durable row; `audit_sink_ready` red | 🟢 (precedented by T-E sink-down drill, `test_sp_op_recurso_001.py`) |
| **C1-part** | **Network partition** worker↔engine / engine↔PG | `toxiproxy`/`pumba` cut between components | in-flight call times out as `CibSevenError`/emit error → fail-closed, no partial effect on the far side | task returns to engine; no un-audited start | 🔴 (needs toxiproxy sidecar — not in stack/deps) |

**Note on C1-part / C2-failover in-process approximations (still 🟢, but honestly labeled):** a
transport-timeout fault (inject a hang/`httpx.TimeoutException` at the `CibSevenTransport` seam) and
a connect-refusal fault (point `PostgresAuditSink` at a dead port) are CI-runnable and prove the
**fail-closed-on-loss** behavior. They are NOT a substitute for proving **recovery/failover**; that
half is genuinely external.

## 3. BUILD-NOW vs BLOCKED-ON

### BUILD-NOW (🟢 — lean stack, existing `integration` marker, no container control)
- **A1, A2, A3** — cross-process/own-start correctness + bridge negative certification.
- **B1a, B1b** — seam-level crash-between-seams convergence (deterministic fault injection; no real
  process kill). B1a directly discharges the `audit_postgres.py:310` "kill-test" the code already
  promises.
- **C1-down** — DB/sink-down fail-closed drill (extend the T-E precedent to the handoff + completion
  paths).
- In-process transport-timeout / connect-refusal fail-closed variants (labeled as loss-not-recovery).

**Rationale:** all run against the already-provisioned `docker compose --profile core` stack with the
real engine + real PG; fault injection is at the Python seam (patch `emit_once`/transport/sink), so
they are fast, deterministic, and do NOT perturb the shared engine state of sibling integration
tests.

### BUILD-NOW-BUT-ISOLATED (🟡 — needs container control → separate CI job, serialized)
- **B1c** (real worker pod-kill), **B2** (daemon restart + readiness gate), **B3** (engine restart).

**Rationale:** these physically stop/kill/restart containers, which is **destructive to the shared
`core` stack** — running them in the same job as A/B1/C1-down would corrupt the engine/PG state those
tests depend on. They require their OWN isolated stack. Two harness options (see §5): (a)
**testcontainers** (already a dep) for per-test isolated postgres+cibseven the test controls; or (b) a
dedicated `docker compose -p chaos` project torn down per suite. Either way they run in a **new,
serialized CI job** (`chaos` matrix), NOT the main integration lane.

### BLOCKED-ON (🔴 — external infra the CI cannot provide)
- **C1-part** (true network partition) — minimal harness that WOULD run it: a `toxiproxy` container
  wired between worker↔engine and engine↔PG, with the test driving toxiproxy's API to cut/restore
  links. **External blocker:** add `toxiproxy` to the chaos compose profile + `toxiproxy-python` dep.
- **C2-failover** (true DB failover) — minimal harness: a 2-node Postgres HA topology (Patroni or a
  local Aurora-like primary/replica with a promotable standby) + a pooler (pgbouncer/HAProxy) the test
  can fail over. **External blocker:** the lean single-PG stack cannot fail over to anything; this
  needs a heavier environment (or a managed Aurora staging) CI does not run today.

**Design the seam now, do not build:** both 🔴 suites get a written harness spec + a fail-closed
invariant table (above) and a skipped-with-loud-reason placeholder test so the lane auto-activates
when the infra lands (mirrors the engine/PG could-not-verify skip pattern).

### Verification protocol — mutation checks (a chaos test is real ONLY if it FAILS when the mechanism is broken)
Each suite ships a paired **mutation assertion** (run under a `MAEZO_CHAOS_MUTATE=<id>` guard or a
`monkeypatch` variant that the harness's mutation-check scaffold drives). The suite is accepted only
if the mutation makes it RED:

| Suite | Mutation that MUST turn the suite red |
|---|---|
| A1/A2 | patch `start_process_idempotent` to skip `find_active_instance` (always start) → "exactly one instance" fails (2 actives) |
| A3 | wire the bridge through the real fenced chokepoint → the fail-open assertion flips (proves A3 tracks the real state, not a constant) |
| B1a | move the chain-insert OUTSIDE the advisory-lock txn → crash-between leaves an orphan link → `verify_chain` gap detected |
| B1b/B1c | reorder to effect-BEFORE-emit (`transport.py` mutation) → crash leaves an un-audited start → "one audit precedes each effect" fails |

## 5. Risks & policy questions

1. **CONTAS→RECURSO→FRAUDE is unwired (build dependency).** The named T3.3 chaos target does not run.
   *Policy question:* does T3.3 scope include **wiring** the `NotificationBridge` through the fenced
   chokepoint (a real engineering task: give it a real `cibseven_starter` that calls
   `start_process_idempotent` with business_key+audit_sink+provenance, a Kafka consumer, an
   `integrations` entrypoint module, and fail-CLOSED `execute_handoff`), or only chaos-testing the
   already-real paths + pinning the gap via A3? Recommendation: **A3 now** (no false L0), and file the
   bridge-wiring as an explicit predecessor task before its chaos suites can exist.
2. **AUTH→ESCALATION causal edge is not wired.** ESCALATION-001 start is real/idempotent, but no
   rafael→helena event exists. Chaos-testable target = ESCALATION-001 start-idempotency (A2), not an
   AUTH→ESCALATION chain. Confirm the plan means the former.
3. **The engine does not enforce business-key uniqueness.** Idempotency rests on the racy
   `find_active_instance` + external-task lock. B1c/B3 must probe the lock-expiry double-start window
   honestly; if the window is real, that is a **product finding**, not a test bug.
4. **Container-control chaos vs the shared CI stack.** Must be a separate serialized job or it
   corrupts sibling integration tests. Adds CI time (engine boot 90s × serialized suites).
5. **testcontainers on `ubuntu-latest`** works (Docker present) but adds image-pull + boot latency;
   budget the `chaos` job accordingly, or gate it to `push`/nightly rather than every PR.
6. **DB-failover honesty.** Do NOT let a DB-**down** drill masquerade as DB-**failover**. The former
   is 🟢 (fail-closed on loss); the latter is 🔴 (recovery/continuity) and needs HA infra.

## 6. External-blocker list (honest)

  replica + pooler). The lean single-PG CI stack cannot provide it. → external; staging/Aurora only.
- **EB-3 (prereq, not infra):** CONTAS→RECURSO→FRAUDE + FRAUDE→* chaos suites are blocked on the
