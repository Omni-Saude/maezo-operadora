# T0.3 — agent.yaml Drift Report (spec/agents/ vs src/maezo/agents/)

**Task:** T0.3 — Single artifact source of truth for agent definitions (defect B14).
**Date:** 2026-07-16
**HEAD at time of audit:** e1c0b34

## Scope

Every one of the 10 agents shipped `agent.yaml` in *two* places:

- `spec/agents/<name>/agent.yaml` — scaffolded once in the greenfield-foundation
  commit (`d4e6189`, "feat: greenfield v2 foundation — spec, infra, plan") and
  never touched again.
- `src/maezo/agents/<name>/agent.yaml` — actively maintained alongside the
  agent's `graph.py` implementation (touched in `255a637` "feat(P2): 8 agent
  graphs + Alembic migrations" and `7e76006` "feat(M5): Agent Framework + A2A +
  MCP Servers").

Additionally, `src/maezo/agents/_template/agent.yaml` (the canonical contract
template referenced by `CONTRIBUTING.md` and `tests/unit/agents/test_template.py`)
had **no counterpart at all** under `spec/agents/`.

## Method

For each of the 10 agents: `diff -u spec/agents/<name>/agent.yaml
src/maezo/agents/<name>/agent.yaml`. Direction of truth was verified per-file
with `git log --oneline -5 -- <path>` (not assumed) and, for the one case with
substantive content drift (carolina), cross-checked against the actual
`graph.py` implementation and its unit tests to confirm which persona is the
one actually running in code.

## Direction of truth: `src/` → `spec/` for all 6 (no exceptions)

For every drifted file, `spec/agents/<name>/agent.yaml` was touched exactly
once (the greenfield scaffold, `d4e6189`) and never again, while
`src/maezo/agents/<name>/agent.yaml` was touched afterwards during real
implementation work. That alone would justify treating `src/` as current, but
one file (carolina) has a drift severe enough to warrant independent
confirmation rather than trusting the git-log heuristic alone:

- **carolina**: `spec/agents/carolina/agent.yaml` describes a completely
  different persona — "Analista de Credenciamento e Gestao de Rede"
  (provider credentialing/network management, `security_zone: phi`,
  `SP-OP-CRED-001`). `src/maezo/agents/carolina/agent.yaml` describes
  "Analista de Revenue Cycle / Pagamentos" (payment validation/execution,
  `security_zone: general`, `SP-OP-PAGTO-001`). These are not a
  reformat/trim of the same content — they are two different agent
  definitions. Cross-checked against
  `src/maezo/agents/carolina/graph.py` (docstring: "Carolina — Revenue
  Cycle / Payment Analyst Agent (Phase 2, PAGTO)"; nodes
  `validate_payment` / `route_approval` / `execute_payment`) and
  `tests/unit/agents/test_carolina.py` (asserts `data.get("phase") == 2`,
  checks for `validate_payment`/`route_approval`/`execute_payment` graph
  nodes). **The implementation and its tests match the `src/` persona.**
  The `spec/` persona (credentialing) was an early greenfield placeholder
  that the agent's real scope moved away from before implementation
  started; it does not describe anything that exists in code today.
- **gustavo, lucas, marina**: `src/` is a comment-stripped copy of the same
  persona/contract (identical `tools`, `autonomy_actions`, `kpis`,
  `escalation.triggers`, `a2a.*`) plus three fields absent from the
  `spec/` scaffold: `phase`, `autonomy_level`, `process_keys` (all three are
  now required/defaulted fields on `AgentDefinition`, see
  `src/maezo/agents/__init__.py`). No semantic conflict — `src/` is a
  strict superset.
- **helena, rafael**: smallest diffs — `src/` adds `phase`,
  `autonomy_level`, `process_keys` and a `# Portado de
  spec/agents/<name>/agent.yaml` provenance comment; one comment line
  trimmed. No semantic conflict — `src/` is a strict superset.

**Decision: for all 6 drifted files, `src/maezo/agents/<name>/agent.yaml` is
copied into `spec/agents/<name>/agent.yaml` verbatim, then the `src/` copy is
deleted.** No exceptions to the general direction were required.

`src/maezo/agents/_template/agent.yaml` had no `spec/` counterpart at all; it
was copied to the new `spec/agents/_template/agent.yaml` (no drift to
reconcile — a straight port) before the `src/` copy was deleted.

## Packaging note (documented only, not fixed — B1/B14 scope)

`pyproject.toml` declares `[tool.hatch.build.targets.wheel] packages =
["src/maezo"]` (hatchling default: includes all files under that tree,
respecting VCS ignore rules). Before this change, the built wheel therefore
shipped all 11 `agent.yaml` files as package data. After this change, the
wheel contains **no** `agent.yaml` files — they live only in `spec/agents/`,
which is not part of the `src/maezo` package tree and is not currently added
to `[tool.hatch.build]` as extra package data.

Any deployment/runtime environment that previously relied on `agent.yaml`
being present inside the installed package (or the container image built
from it) must now also ship/mount the `spec/` directory (or at least
`spec/agents/` and `spec/policies/`, since `autonomy_policy:
../../policies/autonomy` in each `agent.yaml` is a relative reference into
`spec/policies/`) and set `MAEZO_SPEC_DIR` to point at it if it is not laid
out at the conventional `<repo_root>/spec` path relative to the installed
`maezo` package. The Helm chart (`deploy/helm/maezo-tenant/...`) already
has its own `effective-agent-definition.yaml` ConfigMap
mount/merge mechanism (see `templates/configmap-agent-definition.yaml`,
`templates/deployment-agent-runtime.yaml`) that is independent of the
in-package `agent.yaml` — that mechanism is unaffected by this change, but
its "falls back to the harness default (raw L0 agent.yaml)" comment
(`configmap-agent-definition.yaml:44`) implicitly assumed the file shipped
inside the package/image. Wiring the Helm chart to mount `spec/agents/`
(or updating that fallback comment) is out of scope for T0.3 and left to
B1/B14 follow-up, per the task charter ("just document, don't fix here").
